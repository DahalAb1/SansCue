# Topics and questions: candidate preview pipeline

This is an independent Rust service with its own PostgreSQL database. It accepts only the canonical SansCue transcript envelope from the Bee worker on the private service network, stores it idempotently, projects it into one generation job, and produces one development candidate per accepted transcript event. Its own transactional candidate outbox retries delivery to Sessions. No service reads another service's database.

`stub-v1` is a deterministic, explicit placeholder: `What is the key implication of: <excerpt>?`. It is not an AI/model result and is not evidence that a proposed question is useful. Candidate evidence preserves the originating conversation UUID, receive ordinal/time, and excerpt. A production/model generator, topic context, job leasing/backoff/dead-letter policy, and candidate review/edit lifecycle are future work.

Run the service with `TOPICS_DATABASE_URL` pointing only to its own DB, `TOPICS_BEE_SERVICE_TOKEN` shared with the Bee outbox worker, `SESSIONS_INTERNAL_URL` pointing to Sessions' private listener, and `SESSIONS_TOPICS_SERVICE_TOKEN` shared with Sessions. The service exposes health/readiness and authenticated `POST /internal/v1/transcript-events`; the sessions private endpoint consumes candidates. No public candidate endpoint exists. Sessions validates that the conversation, room, bound speaker session, and open-room state match before storing; it exposes previews in room snapshots only to speaker/TA memberships. There is no publication path and candidates never appear to audience members.

The Bee worker persists the accepted canonical event and its delivery outbox row in the same Bee DB transaction. Repeated delivery is safe: Topics verifies the stable event ID against a projection hash and creates one job; Sessions verifies/deduplicates the candidate, then records the room event in its own transaction. Transient outbox delivery failures retry while allowing unrelated rows to progress. Explicit invalid/conflicting transcript events and permanently stale candidate callbacks are recorded as terminal rejections with machine-readable codes; they are not retried indefinitely. An identical candidate callback replayed after its original acceptance remains an accepted duplicate even if the room was subsequently ended or unbound.

This boundary has been exercised through the synthetic replay adapter only. **REAL BEE DEVICE / LIVE API VERIFICATION** remains external and unverified; this code does not implement or claim any live Bee transport. Docker startup and cross-service PostgreSQL acceptance must be verified separately.
