# Transcript-to-candidate v1 boundary

Bee posts the serialized `bee_connection::domain::ConversationEvent` shape to Topics over an authenticated private connection. The envelope uses `schema_version=1`, a stable internal `event_id`, binding (`conversation_id`, optional source conversation identity, `room_id`, `session_id`), arrival `ingest_ordinal`, receive time, optional source identity/sequence, and transcript `text`. Arrival ordinal is not claimed to be speech order. Topics accepts only non-nil identities, positive bounded ordinal, supported schema, and non-empty bounded text.

Topic ingress writes an immutable transcript projection and idempotent `generation_jobs` row; it does not run generation inline. The event UUID is the job idempotency key. A repeated event with the exact same serialized projection is accepted; reuse of its identity with different data is rejected. One deterministic candidate per transcript event is an explicit temporary development cadence, not a product frequency decision. The provider-neutral generator receives only the event as `GenerationInput`; `stub-v1` is the sole active implementation and makes no provider/model call. Evidence is built from the same event's original conversation/ordinal/time/text.

Jobs transition through pending, leased processing, complete, or terminal failure. Claims increment attempts and use UUID fencing tokens, expiry/reclaim, and a lease heartbeat. Every generation call is bounded by a 30-second default deadline; a timeout cancels the future, stops/joins the heartbeat, clears the owned lease, and schedules a retryable `generation_timeout`. Completion writes the candidate and candidate-outbox row in the same transaction as the fenced complete transition. Transient failures use bounded exponential retry; invalid output is permanent, and retries stop at the per-job five-attempt default bound. Candidate delivery has separate outbox state and is polled independently from generation so a slow generator does not pause retries.

Candidate delivery is an at-least-once service outbox: candidate ID equals event ID under the current one-candidate-per-event rule. A new callback is accepted only if the bound conversation and bound speaker session match and the room is still open. A repeat of an already-accepted identical callback is acknowledged as a duplicate before checking current room/binding state; reusing its ID with different immutable content conflicts. Permanently stale or invalid callbacks receive explicit terminal codes and are removed from the retry set, while transient errors remain retryable; processing continues to unrelated outbox rows. Only speaker/TA room snapshots contain these unpublished candidates. Candidate storage has a database constraint that disallows `published=true`; there is no API for publishing or audience access.

Each service owns its DB. Cross-service queries/transactions and shared business-model crates are prohibited; only this versioned JSON contract crosses services. Live Bee payload and source identity/order semantics remain unverified.
